fix: 更新检查不再超时 —— 发行列表改用 tags 接口

现象
- 点「检测更新」报：无法读取社区发行列表：更新网络连接失败（ECONNRESET），
  请检查更新代理或网络；releases.atom 降级失败：GitHub 超时

根因
不是网络不通，是主路径的接口太重：
  GET /repos/<owner>/<repo>/releases?per_page=20
每个 release 的 body（发布说明正文）就有 89 KB，20 条累积 897 KB。
实测该响应完整下载需 34 秒，而 download() 的超时预算是 30 秒
（release 列表路径经 requestUpdate 默认 12 秒），正文传不完就断流，
报成 ECONNRESET / 更新网络连接失败。
首字节只要 0.27 秒，证明链路本身通畅，纯粹是响应体过大。

降级路径同样不可用：
  releases.atom 与 releases/download/* 都在 github.com 上，
  部分网络下该域名不可达，故 atom 降级必然失败并报「GitHub 超时」。

改动
1) lib/community.js — releasedVersions() 改为两步取数据
   - 先拉 /tags（仅名字与 sha，约 5 KB，实测 0.7 秒）拿到全部版本号；
   - 再只对前 8 个候选版本查 /releases/tags/<tag>（约 60 KB/次）
     拿 assets，取 community tgz 与 SHA256SUMS.txt 的 download URL；
   - 单个版本查不到（无正式发行 / 网络抖动）不影响整张列表；
   - 判定仍只看 tag_name 与 assets，正文内容从不参与。
   实测 11 秒内返回 8 个版本（原为 35 秒超时）。

2) lib/update-net.js — 新增 listReleaseTagsFromApi()
   与 listReleaseTagsFromAtom 返回结构一致，但走 api.github.com 的 /tags
   而非 github.com 的 atom 源，实测 1.8 秒返回 30 个 tag。

3) lib/update.js — 降级链改为「releases.atom → api.github.com tag 列表」
   atom 不可用时再试 API 版；两者都不可用才报错，错误信息合并两侧原因。
   同时给 listForkReleases 成功路径补上 degraded: ""，避免下游插值出 undefined。

验证结果
- node --check：community.js / update.js / update-net.js 全部通过
- 端到端：listForkReleases 9.2s 取到 8 个版本，error 为空；
  降级路径 1.8s 取到 30 个 tag
- 测试套件与改动前基线完全一致（323 tests / 278 pass / 23 fail / 22 skipped，
  失败项为 MSYS tar 路径解析的 Windows 环境差异，与本次改动无关）；
  update-status / update-http / update-download / update-policy 四项 34/34 通过

保留事项
- 下载地址仍取 API 返回的 browser_download_url，不做地址改写；
- SHA256SUMS 强校验逻辑未动；
- GITHUB_TOKEN / GH_TOKEN 支持未动（仍可用于提升 API 额度）。
